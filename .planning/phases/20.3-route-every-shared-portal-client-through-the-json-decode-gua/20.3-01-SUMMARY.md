# Plan 20.3-01: Route every shared portal client through the decode guard

## What shipped

`decode_json()` and `decode_json_bytes()` in `shared/http.py`, with all 14 decode
sites across ArcGIS Hub, Socrata, OGC WFS, the geojson parsers and `api_get`
routed through them. Both raise `httpx.DecodingError` — an `HTTPError`, not a
`ValueError` — so a malformed body bypasses the `INVALID_INPUT` arms.

## Corrections made during the phase

- **The structural test found two sites manual review missed.**
  `arcgis_hub._parse_raw_json` and `parsers._parse_geojson` are the real decode
  path for ArcGIS FeatureServer responses — `f=geojson` reads `.content`, so they
  use `json.loads`, which a grep for `response.json()` misses.
- **The first behavioural test was wrong, not the fix.** It injected
  `JSONDecodeError` at the client function, downstream of the shared decoder —
  a path that can no longer occur. Confirmed saskatchewan/manitoba clients hold
  no direct `.json()` call before concluding the test was at fault.
- **A stale caveat was retired.** Phase 20.1 recorded that the full live suite
  stalls on Drug/Nutrient and 20.2 excluded them on that basis without retesting.
  It does not reproduce: 23 tests in 6.5s, all 340 together in 3m24s.

## Codex review (PR #4) — finding valid

`UnicodeDecodeError` is what a body that is not valid UTF-8/16/32 raises, not
`JSONDecodeError`, and it also subclasses `ValueError`. I had considered it
earlier and dismissed it as speculation. Fixed in both helpers and in
`upstream_guard`, which had the same arm ordering.

Worth recording: my first verification of that report used `b"\xff\xfe\x00bad"`,
a valid UTF-16 BOM, which decoded and failed as `JSONDecodeError` — appearing to
contradict Codex. Only the exact reported byte showed the real behaviour.
