4. **Audit the PRESERVE list** — the ~10 deliberately-tolerant tests — so each one

**Out of scope:** the same defect class in *unit* tests (see Deferred Ideas). New
tools, new modules, new provinces.

<decisions>
## Implementation Decisions

### Scope — all four workstreams are in

- **D-01:** All four areas are in scope: fix the 17 live failures, finish de-masking
  (weather + BC + YR + AB), add a reintroduction guard, audit the PRESERVE list.
- **D-02:** **Definition of done:** the phase closes only when the live integration
  suite is fully green, OR every remaining failure has a written, accepted reason
  recorded in the phase artifacts. No repeat of quick-1's silent 17-item deferral.
  — **Reversibility:** reversible — a scope decision, not a code contract.
- **D-03:** Rename the phase. The ROADMAP title describes finished work and the goal
  is still the placeholder `[Urgent work - to be planned]`. Update both to describe
  what the phase now does. Do this during planning, before any implementation.

### Failure triage policy

- **D-04:** Per failure, decide whether the **tool** is broken or the **test** has
  drifted, and fix whichever is actually wrong. Not test-first, not code-first.
- **D-05:** For the shape-drift cluster (BOC, York Region, StatCan bulk_vector —
  `data["data"]` is a dict where tests expect a list): **case by case**. Some may be
  genuine multi-key responses (a dict keyed by series/vector is defensible); others
  may be accidental drift away from the `flatten responses aggressively` rule in
  CLAUDE.md. The planner must inspect each and justify the call in the plan.
  — **Reversibility:** costly — changing a tool's `data` shape breaks every caller,
  the README examples, and any agent relying on the documented envelope. Decide once,
  per tool, with the reason written down.
- **D-06:** **BOC specifically — investigate before deciding.** 5 failures come from
  one shape change. Check git history for when `boc_get_exchange_rates` began
  returning a dict. If it was a deliberate commit there will be a rationale and
  possibly a summary; if it drifted in unnoticed, it is a regression in a v1.0
  module with documented list-shaped README examples. Research answers this — do not
  guess during planning.
- **D-07:** Toronto's two live-API clusters (TTC GTFS unreachable, CKAN ReadTimeout
  on long runs) get the hardened pattern (D-08), not a code fix — subject to D-09.

### Transient-failure policy

- **D-08:** **Alberta hardened pattern is the project standard.** A test may keep an
  error branch, but it must assert the code is in `{UPSTREAM_ERROR, RATE_LIMITED}`
  and nothing else. A genuine outage stays green; a `NOT_FOUND`, `INVALID_INPUT`, or
  unexpected code still fails loudly. Reference implementation:
  `test_alberta_road_events` in `tests/integration/test_tool_scenarios.py`.
- **D-09:** Before tolerating an endpoint under D-08, confirm it is transiently down
  rather than permanently gone. A dead endpoint tolerated forever masks a dead tool —
  which is the exact failure class this phase exists to end. TTC GTFS specifically
  needs this check.

### De-masking approach

- **D-10:** **Weather is IN**, with the hardened pattern. 18 guards across 4 files,
  34 tools — the largest and least loudly-tested module. ECCC/GeoMet flakiness is
  real, so strict-no-error would leave the suite permanently red, but the current
  silent guards hide wrong error codes and bad payloads just as well as real outages.
- **D-11:** **BC's 5 `pytest.skip` calls are masks** — "BCDC search returned no
  results" silently means the WFS-routing path was never exercised. Fix by **pinning
  to a known-stable package id** so the test always runs. (Considered and not chosen:
  keeping dynamic discovery but failing instead of skipping.)
- **D-12:** **One plan per module** — weather / BC / York Region / Alberta each
  de-masked and live-run before moving to the next, so newly-surfaced failures are
  attributable to the module that caused them. (Considered and not chosen: one sweep
  then one run; grouping by idiom.)

### Reintroduction guard

- **D-13:** Mechanism is **Claude's discretion** (see below). The hard requirement:
  reintroducing a mask must fail something automatically, without a human noticing.
  `tests/test_quality.py` is the existing precedent — it fails the default unit suite
  when a tool docstring lacks `Keywords:`. The guard should likewise run in the
  **unit** suite, not only the live run, so it is enforced on every commit.
- **D-14:** **PRESERVE tests declare themselves with a pytest marker**, e.g.
  `@pytest.mark.tolerates_upstream_error(reason="off-season empty is valid")`.
  Structured and queryable, unlike a comment. The marker must be registered in pytest
  config. The guard allowlists marked tests and fails any other tolerant test; the
  audit flags any marked test whose reason is missing or no longer true.
  — **Reversibility:** reversible — a test-only convention.

### Claude's Discretion

- **Guard implementation** (D-13): AST-based structural check vs. regex on the known
  idioms vs. another mechanism. AST catches idioms nobody has written yet; regex is
  more legible. Ruff custom rules were raised but conflict with the project's fixed
  dependency policy — prefer a test. Research/planning picks.
- Plan count and task breakdown within each module's plan.
- Whether the PRESERVE audit is its own plan or folded into each module's plan.

</decisions>

### Operational note for the planner — the live suite has slowed sharply
Quick-1 recorded the full live suite at **219s**. A re-run started during this
discussion was still going at **20 minutes** with only 37s of CPU — i.e. blocked on
network, not computing. That is consistent with more upstreams timing out than in
June (each unreachable endpoint burns up to the 120s timeout). Two implications:
1. Budget far more wall-clock per live run than quick-1 did. D-12's one-run-per-module
   approach makes this worse — consider running only the affected module's tests
   between plans and the full suite once at the end.
2. The slowdown itself may be a finding. Some of the 17 may have degraded from
   "fails fast" to "hangs", and there may be new failures beyond the 17.
**The planner must re-measure the live baseline before planning task breakdown — do
not assume the 17-failure list from June is still accurate.**

<specifics>
## Specific Ideas

- The masking pattern is the *symptom*; the disease is tests that cannot fail. Quick-1
  named it precisely: "ship broken, tests green", demonstrated by the NS
  health-facilities 400 bug in Phase 20-08. Every decision here is aimed at that.
- The guard (D-13) matters more than any individual de-masking. Without it, the next
  module author copies the nearest example and the pattern returns a third time.

</specifics>

<deferred>
## Deferred Ideas

### The same defect class in UNIT tests — its own phase
Work on 2026-07-25 found the identical failure mode one layer down, and integration
de-masking will not catch it:
- `statcan/__tests__/test_client.py` built expected values with
  `FREQUENCY_CODES.get(...)` — asserting the map under test against itself. It passed
  for any map, and shipped one that reported monthly CPI as "Bi-monthly" for three
  phases.
- `statcan/__tests__/conftest.py` fixtures were fabricated to match the wrong map
  (monthly CPI given `frequencyCode: 5`, which is not a StatCan code at all).
- Three separate hand-written reference catalogs were wrong, one of them
  (`data://statcan/uom-codes`) in all 15 entries.

Fixed for StatCan only. Other modules embed similar static catalogs and may have the
same self-referential assertions. A sweep for the pattern — tautological assertions,
fabricated fixtures, hand-transcribed reference data with no upstream check — is worth
its own phase. Out of scope here: 20.1 is about integration tests.
