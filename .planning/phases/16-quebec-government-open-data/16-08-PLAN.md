<objective>
Fix the route filter substring match bug in `fetch_bridge_structures`: `route='A-20'` returns Route 204 bridges instead of Autoroute 20 bridges because `raw_digits="20"` is a substring of `"route 204"`.

Purpose: The nom_route fallback at line 704 uses `raw_digits not in nom` which is a substring check. `"20" in "route 204"` is True, so Route 204 rows pass the filter. The primary num_route exact match correctly rejects these rows, but the fallback overrides it. Removing the fallback fixes the bug.

Output: Bridge route filter returns only exact num_route matches. One line change + one new unit test class + tightened integration assertion.
</objective>

## The bug — client.py lines 694-705

```python
# Post-parse filtering
norm = _normalize_route(route) if route else None
out: list[QuebecBridgeStructure] = []
for r in all_rows:
    if norm is not None:
        num_raw = r.get("num_route")
        num = _normalize_route(str(num_raw)) if num_raw is not None else ""
        nom = str(r.get("nom_route") or "").lower()
        # Match zero-padded num_route OR nom_route contains the raw digits
        raw_digits = norm.lstrip("0") or "0"
        if num != norm and raw_digits not in nom:  # <-- LINE 704: BUG
            continue
```

**Problem:** `raw_digits="20"` (from "A-20") matches inside `"route 204"` because `"20" in "route 204"` is True. The primary `num != norm` check correctly rejects Route 204 rows (since `_normalize_route("204")` = `"00204"` != `"00020"`), but the nom_route fallback lets them through.

**Fix:** Remove the nom_route fallback entirely. Replace line 704 with:
```python
        if num != norm:
            continue
```

This is safe because `_normalize_route` already handles all user input formats ("A-20", "Autoroute 20", "20", "00020") and the num_route exact match is the reliable path. The nom_route fallback was added as a safety net but introduces the substring bug.
