# Plan 20.2-01: Catch-all coverage for every tool + decode guard in api_get

## What shipped

An AST sweep over all 271 `@tool` functions found **108 with no catch-all**: 68
caught only `httpx.HTTPStatusError`, 41 caught nothing at all, 15 caught only
`WfsError`, 12 caught `ValueError` + `HTTPStatusError`. A timeout, connect error
or malformed body escaped every one of them as a raw fastmcp `ToolError` — the
same condition Phase 20.1 fixed for drug_database and nutrient_file, never
generalised. All 108 now carry `@upstream_guard(<api_name>)`.

Second defect: `json.JSONDecodeError` subclasses `ValueError`, so an upstream
HTML error page raised out of `api_get` landed in the
`except ValueError -> INVALID_INPUT` arms of seven modules. `api_get` now raises
`httpx.DecodingError`.

## Corrections made during the phase

- **A first count of 136 was wrong.** york_region's 28 tools delegate to a
  `_call_client` helper that already handles broad failures. Found by
  spot-checking a flagged tool rather than trusting the number; the detector now
  resolves module-level helper delegation.
- **An import rewrite bug was caught before commit.** The transformer treated a
  trailing `# noqa` comment in `alberta/tools.py` as an import item, burying
  `upstream_guard` inside the comment. Caught by importing all 29 tool modules,
  not by reading the diff.

## Codex review (PR #3) — both findings valid

- `upstream_guard` was **not** a real catch-all (httpx + JSONDecodeError +
  ValueError only), so a `KeyError` from flattening still escaped — and
  `test_tool_error_handling.py` counted the decorator as proof of coverage,
  making the result unearned. Fixed with `except Exception`, plus a test that
  verifies the guard's own premise.
- `pydantic.ValidationError` also subclasses `ValueError`, so upstream schema
  drift was reported as caller error. Now `UPSTREAM_ERROR`.

## Verification

3145 unit tests, 97.09% coverage; 273 tools still register through MCP with
parameter schemas intact; CI green on Python 3.12/3.13/3.14.
