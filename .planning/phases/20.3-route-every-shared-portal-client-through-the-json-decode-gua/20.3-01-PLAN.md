# Plan 20.3-01: Route every shared portal client through the JSON decode guard

<objective>
Finish the decode guard Phase 20.2 applied to `api_get` alone, so a malformed
upstream body is classified as an upstream failure on every portal technology.
</objective>

## Findings that shaped the plan

| Client | Decode form | Guarded by 20.2? |
|---|---|---|
| `shared/http.py` (CKAN family) | `response.json()` | yes |
| `shared/arcgis_hub.py` | `response.json()` ×6 + `_parse_raw_json` | **no** |
| `shared/socrata.py` | `response.json()` ×6 | **no** |
| `shared/ogc.py` | `json.loads(response.content)` ×2 | **no** |
| `shared/parsers.py` (geojson hot path) | `json.loads(content)` ×2 | **no** |

Reproduced before fixing — `saskatchewan_get_fire_bans` and
`manitoba_get_livestock_prices` both returned `INVALID_INPUT` for a malformed
body. So `ERR-03` was true for CKAN modules and overclaimed elsewhere.

## Tasks

- [x] **RED** — behavioural probe proving the five affected tools mislabel
- [x] **GREEN** — `decode_json()` / `decode_json_bytes()` in `shared/http.py`;
      all 14 decode sites routed through them, `api_get` included
- [x] **Guard** — `test_no_shared_portal_client_decodes_json_unguarded` fails if
      a raw decode reappears in `shared/`
- [x] **Codex P2** — `UnicodeDecodeError`, not `JSONDecodeError`, is what an
      invalid byte encoding raises, and it also subclasses `ValueError`. Fixed in
      both helpers and in `upstream_guard`, which had the identical arm ordering

## Deliberately not done

The five tool-level tests inject `httpx.DecodingError`, which the tools' catch-all
already handled after 20.2 — they pass with or without this change and are
forward-looking regression guards, not evidence. The four shared-client tests are
the proof.
